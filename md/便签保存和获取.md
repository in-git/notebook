# C端用户便签对接精简文档（开发对接专用，剔除冗余描述，直接给开发/AI生成代码）

## 一、接口总览

| 接口                          | 方法 | 用途         | 鉴权     |
| ----------------------------- | ---- | ------------ | -------- |
| `/client/c/userNote/save`     | POST | 保存便签内容 | C端登录态 |
| `/client/c/userNote/get`      | GET  | 获取便签内容 | C端登录态 |

> 两个接口均位于 `/client/c/**` 前缀下，系统 Sa-Token 拦截器自动走 C 端 `StpClientUtil` 校验，**不能**使用 B 端 token (`StpUtil`)。

## 二、保存便签 `/client/c/userNote/save` POST

### 入参

| 参数     | 位置            | 必填 | 类型                | 说明                                  |
| -------- | --------------- | ---- | ------------------- | ------------------------------------- |
| userId   | query string    | 是   | string              | C 端用户ID（雪花ID）                  |
| jsonData | request body    | 是   | string（**纯文本**） | 便签内容，**前端必须自己 JSON 序列化** |

### 关键约束

- `jsonData` 通过 `@RequestBody String` 接收，**Content-Type 必须为 `text/plain`**，**不能**是 `application/json`
- `userId` 通过 `?userId=xxx` 拼在 URL 上，**不能**放在 body
- 不做字段校验、不做长度限制，**内容完整性由前端控制**

### 请求示例

```
POST /client/c/userNote/save?userId=1900000000000000001
Content-Type: text/plain
Authorization: Bearer <CLIENT_TOKEN>

{"title":"购物清单","items":[{"name":"苹果","qty":3}]}
```

### 返回

| 字段   | 类型    | 说明                              |
| ------ | ------- | --------------------------------- |
| code   | int     | 200=成功，其他见全局错误码        |
| data   | string  | `success`（保存成功标识）          |
| message| string  | 成功时为 `success`                |

成功响应

```json
{ "code": 200, "data": "success", "message": "success" }
```

失败响应（鉴权失败示例）

```json
{ "code": 401, "message": "token失效" }
```

## 三、获取便签 `/client/c/userNote/get` GET

### 入参

| 参数   | 位置         | 必填 | 类型   | 说明             |
| ------ | ------------ | ---- | ------ | ---------------- |
| userId | query string | 是   | string | C 端用户ID（雪花ID） |

### 关键约束

- 无 `jsonData` 参数，**不需要** request body
- 仅按 `userId` 唯一查找，返回该用户最新一份便签

### 请求示例

```
GET /client/c/userNote/get?userId=1900000000000000001
Authorization: Bearer <CLIENT_TOKEN>
```

### 返回

| 字段    | 类型                | 说明                                                |
| ------- | ------------------- | --------------------------------------------------- |
| code    | int                 | 200=成功                                            |
| data    | string \| null      | **纯文本字符串**（与保存时原样写回），**不是 JSON 对象** |
| message | string              | 成功时为 `success`                                  |

成功响应（无便签）

```json
{ "code": 200, "data": null, "message": "success" }
```

成功响应（有便签）

```json
{ "code": 200, "data": "{\"title\":\"购物清单\",\"items\":[{\"name\":\"苹果\",\"qty\":3}]}", "message": "success" }
```

> 注意：`data` 字段外层是 JSON 字符串，**前端需要再 `JSON.parse` 一次**才能拿到原始对象。
> 后端不做 `JSON.parse`，**保存什么字符串就返回什么字符串**。

## 四、前端调用

封装位置：`@/api/dev/userNoteApi.js`，已统一使用 `clientBaseRequest`（带 `CLIENT_TOKEN`）

```js
import userNoteApi from '@/api/dev/userNoteApi';

// 保存：前端自己 JSON.stringify
const jsonStr = JSON.stringify({ title: '购物清单', items: [{ name: '苹果', qty: 3 }] });
await userNoteApi.userNoteSave(userId, jsonStr);

// 获取：拿到字符串后再 JSON.parse
const raw = await userNoteApi.userNoteGet(userId);
const obj = raw ? JSON.parse(raw) : null;
```

> `clientBaseRequest` 自动从 localStorage 读 `CLIENT_TOKEN` 塞到 `Authorization` 头，**前端不要再手动塞 token**。

## 五、典型时序

### 5.1 首次进入便签页（获取）

```
[页面加载]
   │
   ▼
GET /client/c/userNote/get?userId=<id>
   │
   ├─ data != null → JSON.parse(data) → 回显便签编辑器
   │
   └─ data == null → 展示空便签编辑器
```

### 5.2 编辑后保存

```
[用户编辑便签]
   │
   ▼
[点击保存]
   │
   ▼
[前端 JSON.stringify 整个便签对象]
   │
   ▼
POST /client/c/userNote/save?userId=<id>
   Body: <序列化后的字符串>    Content-Type: text/plain
   │
   ├─ code=200 → message.success('保存成功')
   │
   └─ code≠200 → 提示 message，**不刷新页面、不清空编辑器**
```

### 5.3 跨设备/刷新页面对账

```
[任一时机，例如 onMounted]
   │
   ▼
GET /client/c/userNote/get?userId=<id>
   │
   ▼
[后端始终返回该 userId 的最新一份内容]
   │
   ▼
前端比对本地版本号或时间戳，决定是否提示用户「远端有更新，是否覆盖」
```

## 六、关键约束（硬性，必须遵守）

1. **C 端鉴权**：两个接口都依赖 C 端 `CLIENT_TOKEN`（localStorage key=`CLIENT_TOKEN`），B 端 token `TOKEN` 调这两个接口会 401
2. **路径前缀**：必须 `/client/c/userNote/...`，**不要**写成 `/dev/userNote/...`（B 端路径会触发 B 端鉴权）
3. **save 的 Content-Type**：必须是 `text/plain`，**不是** `application/json`，**不是** `application/x-www-form-urlencoded`
4. **save 的 userId 在 URL**：通过 `?userId=xxx` 拼接，**不放在 body**
5. **get 的 data 是字符串**：返回 `data` 是纯文本字符串，**不是** 已经 `JSON.parse` 好的对象
6. **不做后端校验**：后端不校验 JSON 合法性、不做字段约束、不做长度限制，**任何字符串都可以保存**
7. **按 userId 一人一档**：每个 C 端用户只有一份便签，**后端 save 是覆盖式（upsert）**，不是追加
8. **不要使用 B 端 api 模块**：必须从 `@/api/dev/userNoteApi.js` 走，**该文件已经统一改用 `clientBaseRequest`**

## 七、典型前端表单字段（参考）

| 字段         | 类型                | 说明                       |
| ------------ | ------------------- | -------------------------- |
| userId       | string              | C 端用户ID，雪花ID字符串   |
| noteContent  | object              | 前端维护的便签对象，任意结构 |
| editorState  | 'idle' \| 'saving' \| 'saved' \| 'error' | 保存状态机 |

> `noteContent` 的内部结构由前端自由定义（例如 `{title, items, lastModify}`），后端只存字符串不解析。
